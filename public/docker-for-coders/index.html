psychologythe pattern

The localhost lab monster's actual problems

None of these are skill problems. They're environment problems — and Docker exists specifically to kill them.

layers

Every project fights for the same Python/Node

Project A needs Python 3.9, Project B needs 3.12. You juggle pyenv, nvm, and virtualenvs, and something always breaks after an OS update.

storage

Databases get installed globally and never leave

brew install postgresql once, and two years later you have three major versions fighting over port 5432 and no memory of how you configured any of them.

forward_to_inbox

You can't hand your project to anyone

Sending a friend your repo means sending them a README of 15 manual setup steps — half of which you've forgotten you even did.

help

"Deployment" is a black box

You can write the logic. You have no idea what actually happens between git push and a real server running your code.

psychology_altthe mental model

Think of it in terms you already know

You already understand classes and instances. Docker's three core concepts map directly onto that.

Dockerfile

The recipe you write

A plain text file of instructions: start from this base, install these dependencies, copy in this code, run this command. It's source code you commit to git.

Like: a class definition — the blueprint, not yet built or running.
arrow_downward
Image

The frozen, built artifact

Running docker build on a Dockerfile produces an image — a versioned, immutable snapshot containing your code and every dependency it needs. It never changes once built.

Like: a compiled build — reproducible, and stamped with a tag like myapp:1.2.
arrow_downward
Container

A running instance of that image

docker run takes an image and instantiates it as a live, isolated process. Spin up five containers from one image — each is independent, and disposable.

Like: an object instantiated from a class. Throw it away, make a new one, no side effects.
boltthe flagship example

"I need Postgres + Redis + my API, running locally"

This exact request is the single most common reason developers first reach for Docker. Here's both paths, side by side.

closewithout docker
  1. brew install postgresql@16 — installs system-wide
  2. initdb, then pg_ctl start, then manually create a user and database
  3. Edit pg_hba.conf because auth rejects your connection
  4. brew install redis, configure it as a background service too
  5. Six months later, a different project needs Postgres 14 — now they collide on the same port and binary
  6. Uninstalling any of it cleanly is its own multi-step project
checkwith docker

One file, checked into your repo:

docker-compose.yml
services:
  api:
    build: .
    ports:
      - "5000:5000"
    volumes:
      - ./:/app
    environment:
      POSTGRES_DB: labdb
      POSTGRES_USER: labuser
      POSTGRES_PASSWORD: labpass
    depends_on:
      - db

  db:
    image: postgres:16
    environment:
      POSTGRES_DB: labdb
      POSTGRES_USER: labuser
      POSTGRES_PASSWORD: labpass
    volumes:
      - pgdata:/var/lib/postgresql/data

  cache:
    image: redis:7

volumes:
  pgdata:
zsh
$ docker compose up -d --build
✔ api, db, and cache all running in ~10 seconds
$ docker compose down -v
✔ everything gone. your machine is exactly as clean as before.

Every file that makes the example above real

A minimal Flask API that talks to Postgres — swap the language, the pattern is identical in Node, Go, or Ruby.

my-project/
├── app.py
├── requirements.txt
├── Dockerfile
├── .dockerignore

app.py
from flask import Flask, jsonify
import psycopg2
import os

app = Flask(__name__)

def get_connection():
    return psycopg2.connect(
        host="db",
        dbname=os.environ["POSTGRES_DB"],
        user=os.environ["POSTGRES_USER"],
        password=os.environ["POSTGRES_PASSWORD"],
    )

@app.route("/health")
def health():
    conn = get_connection()
    conn.close()
    return jsonify(status="ok", db="connected")

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)
requirements.txt
flask==3.0.3
psycopg2-binary==2.9.9
Dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 5000
CMD ["python", "app.py"]
.dockerignore
__pycache__/
*.pyc
.venv/
.git
.env

Notice the volumes: - ./:/app line in the compose file above — it bind-mounts your local folder straight into the container. Edit app.py on your machine, and the running container sees the change instantly. No rebuild, no redeploy, for pure code changes.

swap_horiza second everyday scenario

Running two Node versions without nvm

Project A needs Node 18. Project B needs Node 20. Instead of juggling a version manager, hand each project its own disposable runtime.

zsh
$ docker run --rm -it -v "$(pwd)":/app -w /app node:18-alpine node -v
v18.20.4
$ docker run --rm -it -v "$(pwd)":/app -w /app node:20-alpine node -v
v20.16.0

Both commands ran against the exact same folder on your machine, using two completely different, fully isolated Node installs — neither of which is "installed" on your laptop at all. Close the terminal and both runtimes disappear with it.

translatequick reference

Vocabulary, translated

image What it is: An immutable, versioned snapshot of an app + its dependencies. Think: a compiled build artifact.
container What it is: A running, isolated instance of an image. Think: an object instantiated from a class.
volume What it is: Storage that lives outside the container's lifecycle, so data survives even after the container is deleted. Think: a database file living on an external drive, not the laptop itself.
port mapping What it is: Connecting a port inside the container to a port on your actual machine, e.g. -p 5000:5000. Think: forwarding a call to an extension.
registry What it is: A place images are stored and pulled from, like Docker Hub. Think: PyPI or npm, but for entire environments instead of single libraries.
compose What it is: A YAML file describing several containers that should run together as one stack. Think: package.json, but it declares running services instead of installed libraries.
codecommand reference

The commands you'll actually type

Build & run a single container

docker build -t myapp:1.0 .Build an image from the Dockerfile in this folder
docker run -d -p 5000:5000 myapp:1.0Run it in the background, mapped to a local port
docker run --rm -it python:3.12 bashDrop into a throwaway shell inside a fresh container

Working with compose

docker compose up -dStart every service defined in docker-compose.yml
docker compose up -d --buildRebuild images first, then start everything
docker compose logs -f apiStream live logs from one service
docker compose exec api bashOpen a shell inside a running service
docker compose down -vStop everything and delete its data too

Inspecting & debugging

docker psList running containers
docker ps -aList every container, including stopped ones
docker logs -f myappStream logs from a container by name
docker exec -it myapp bashShell into a specific running container

Cleaning up

docker image pruneDelete unused, dangling images
docker system prune -aNuke every unused image, container, and network
docker volume lsSee what persistent data still exists
reportsave yourself the pain

Mistakes almost everyone makes first

delete_sweep

"My database data disappeared!"

Forgetting the volumes: entry means all data lives only inside the container. Delete the container, and the data goes with it.

sync_problem

Pinning nothing to :latest

postgres:latest can silently become a different major version on a rebuild months later. Pin real versions: postgres:16.

unarchive

Bloated images from skipping .dockerignore

Without it, COPY . . drags your entire node_modules or .git folder into the image, making builds slow and huge.

lan

Forgetting the port mapping

A service running perfectly inside a container is invisible from your browser until you map it out with -p host:container.

admin_panel_settings

Running everything as root inside the container

The default user in most base images is root. Fine for a local lab experiment — worth fixing with a USER instruction before anything goes near a real server.

insights
Where this leads

A compose file running three containers on your laptop is a miniature version of what tools like Kubernetes do across hundreds of real servers — the same core idea of images and containers, just coordinated at a much larger scale. Learning to write a clean Dockerfile and compose file now is the exact on-ramp to understanding real deployment later, and it's the same file a teammate needs to stop depending on your memory of "how you set it up."
