The Smallest Ways to Deliver Python

A Python file is source. Delivery begins when the intended person, machine, server, build system, or browser can actually execute it. Separate the code you author from the interpreter, dependencies, entry point, runtime process, and public surface that make it real.

The Python rule

Python needs an execution environment, not just a file extension.

A lone .py file can be a complete program when the recipient already has a compatible Python interpreter and the script uses only the standard library. Add third-party packages, a web URL, a repeatable install, or browser execution and the real delivery expands.

Terminology correction

“One Python file” can still hide the entire delivery system

The file count tells you how much source you can see. It does not tell you who supplies Python, installs packages, starts the process, maps a URL, injects secrets, or keeps the program alive.

Misleading shorthand

“The feature is just one api.py, so it can go into any website.” A browser cannot natively execute that server-oriented Python file, and a static host cannot keep it running.

api.py ≠ deployed Python behavior

Complete statement

“I author one Python handler; the platform supplies a compatible interpreter, package installation, request adapter, process lifecycle, routing, logs, secrets, and a public URL.”

source + environment + entry point + runtime = delivery
Three meanings of delivery

Handing over code is not the same as handing over behavior

A useful architecture starts by naming who needs to run the Python and where the result must appear.

Source handoff

A developer receives readable Python and instructions. Their machine supplies the interpreter, dependencies, data, and command.

Environment handoff

The project also declares packages, versions, entry points, and perhaps a lockfile or container so another machine can reproduce it.

Service delivery

Users never receive Python. They visit a URL or call an API while a server, function, or Worker executes the code elsewhere.

Output delivery

Python runs only during a build or batch job. Users receive generated HTML, JSON, images, reports, or other static artifacts.

Repository hygiene

Declare the environment; do not usually ship your local environment

Python projects often become confusing because generated local state is mistaken for project source.

Usually commit

.py source, pyproject.toml, intentional requirements or lock files, tests, migrations, templates, static assets, container config, deployment config, documentation.

Usually ignore

.venv/, __pycache__/, *.pyc, tool caches, build output that can be regenerated, local secrets, machine-specific editor state, disposable local databases.

Decision guide

Choose the least machinery that makes the result genuinely runnable

Move up the ladder because the audience or runtime changed—not because a larger Python project looks more professional.

Only you run a small automation?

One machine, known Python version, no third-party packages, no public URL.

Use one standard-library script.

Sharing a script that imports packages?

The recipient can install Python but needs an explicit dependency list.

Add a requirements file or pyproject metadata.

Need a reusable command?

Users should install once and run a named command from anywhere.

Package it and declare a console entry point.

Need dynamic browser-visible behavior?

Requests, secrets, databases, authentication, or private logic must run away from the browser.

Deploy a Flask/FastAPI app, function, Worker, or service.

Existing frontend needs one Python capability?

The main site stays Astro, React, Next.js, or plain JavaScript.

Add a Python function or call a separate Python API.

Python only prepares content?

The final site can be static after data, pages, or assets are generated.

Run Python at build time and publish only the output.

Python must execute on the visitor’s device?

No server round trip, but a larger browser runtime and package limits are acceptable.

Use Pyodide or another WebAssembly Python runtime.

Machine parity matters more than minimal files?

Native libraries, system packages, OS behavior, or production reproducibility matter.

Deliver a container definition and build an image.

Framework structure is already valuable?

Routing, settings, migrations, admin, tests, and team ownership have outgrown one file.

Use the framework’s conventional project layout.
